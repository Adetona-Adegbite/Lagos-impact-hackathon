# Supamart Offline-First Sync Engine Design

## 1. Overview
Supamart operates in an environment with unreliable network connectivity. The system uses a **Local-First** architecture where the mobile app (React Native + SQLite) acts as the primary interface for data creation and modification. The backend (Express + PostgreSQL) serves as the durable source of truth and synchronization hub.

We employ an **Operation-Based Sync** strategy (Event Sourcing lite) rather than state-based syncing to ensure data integrity, especially for inventory and sales.

## 2. Architectural Principles

1.  **Intent over State**: We sync *what happened* (e.g., "Sold 5 items") rather than *what is* (e.g., "Quantity is 45").
2.  **Offline Event Producer**: The mobile app records user actions as operations in a local queue immediately.
3.  **Idempotency**: The server guarantees that processing the same operation ID multiple times yields the same result.
4.  **Append-Only Log**: Operations are never deleted, only appended.
5.  **Deltas for Inventory**: Stock levels are adjusted via deltas (`+5`, `-2`) to avoid race conditions.

## 3. Data Model

### 3.1 Server Schema (PostgreSQL/Prisma)

Existing entities (`Product`, `Inventory`, `Sale`) are augmented with versioning. A new `Operation` table tracks the sync history.

```prisma
enum OpType {
  CREATE
  UPDATE
  DELETE
  ADJUST_STOCK
  CREATE_SALE
}

model Operation {
  id              String   @id @default(cuid())
  clientOpId      String   @unique // UUID generated by client
  userId          String
  user            User     @relation(fields: [userId], references: [id])
  deviceId        String   // Trace source of changes
  entityType      String   // e.g., "Product", "Sale"
  entityId        String   // ID of the entity being modified
  opType          OpType
  payload         Json     // The data content of the operation
  baseVersion     Int?     // Optimistic concurrency control (optional)
  clientTimestamp DateTime // When it happened on device
  createdAt       DateTime @default(now()) // When it arrived on server

  @@index([userId, createdAt])
}

// Entities like Product and Inventory get a 'version' field
model Product {
  // ...
  version Int @default(1)
}
```

### 3.2 Client Schema (SQLite)

The client mirrors core tables but adds an `operations_queue`.

```sql
CREATE TABLE operations_queue (
  id TEXT PRIMARY KEY,           -- UUID
  op_type TEXT NOT NULL,         -- CREATE, UPDATE, etc.
  entity_type TEXT NOT NULL,
  entity_id TEXT NOT NULL,
  payload TEXT NOT NULL,         -- JSON string
  created_at INTEGER NOT NULL,
  synced INTEGER DEFAULT 0       -- 0 = false, 1 = true
);
```

## 4. Sync Protocol

### 4.1 Push (Client → Server)
**Endpoint**: `POST /sync/push`

**Payload**:
```json
{
  "deviceId": "uuid-v4",
  "operations": [
    {
      "clientOpId": "op-uuid-1",
      "opType": "CREATE_SALE",
      "entityType": "Sale",
      "entityId": "sale-uuid-x",
      "payload": { ... },
      "timestamp": "2023-10-27T10:00:00Z"
    }
  ]
}
```

**Server Logic**:
1.  **Authenticate** user.
2.  Start **Transaction**.
3.  Iterate through operations:
    *   Check if `clientOpId` exists in `Operation` table.
        *   If yes, skip (Idempotency).
        *   If no, proceed.
    *   **Apply Operation**: Execute specific logic based on `opType`.
        *   *CREATE*: Insert record.
        *   *UPDATE*: Update record if version matches (or last-write-wins).
        *   *ADJUST_STOCK*: `UPDATE inventory SET quantity = quantity + delta WHERE productId = ...`
        *   *CREATE_SALE*: Insert Sale + SaleItems, trigger stock adjustment.
    *   **Record Operation**: Insert into `Operation` table.
4.  Commit **Transaction**.
5.  Return success with list of processed IDs.

**Client Logic**:
1.  Select `WHERE synced = 0`.
2.  Send batch.
3.  On 200 OK, mark sent operations as `synced = 1` (or delete them).

### 4.2 Pull (Server → Client)
**Endpoint**: `GET /sync/pull?since=<timestamp>`

**Server Logic**:
1.  Query `Operation` table `WHERE userId = ? AND createdAt > since`.
2.  Return list of operations.

**Client Logic**:
1.  Receive operations.
2.  Filter out operations that originated from *this* device (using `deviceId` check inside payload or metadata).
3.  Replay operations locally to update SQLite state.
    *   *Note*: Ideally, the client might just fetch the latest state of modified entities ("State Hydration") instead of replaying raw operations, but replaying operations keeps logic symmetric. For Supamart, **Smart State Hydration** is often safer for the client to ensure consistency.
    *   *Refined Pull Strategy*: The server returns the *latest state* of entities modified since `<timestamp>`, rather than raw operations. This simplifies client logic and self-heals drift.

    **Revised Pull Response**:
    ```json
    {
      "lastSyncTimestamp": "2023-10-27T12:00:00Z",
      "changes": {
        "products": [ { ...full_product_obj... } ],
        "inventory": [ { ...full_inventory_obj... } ],
        "sales": [ ... ]
      }
    }
    ```

## 5. Conflict Resolution Strategy

### 5.1 Mutable Entities (Product, User Profile)
*   **Strategy**: Last-Write-Wins (LWW) based on server arrival time (simplified) or logical clock.
*   Given Supamart is often single-tenant per shop (or few staff), conflicts are rare.
*   **Implementation**: Server overwrites fields provided in payload.

### 5.2 Inventory
*   **Strategy**: Commutative Updates (Deltas).
*   Inventory is never "set to 10". It is "decreased by 1".
*   If Device A sells 1 (Stock 10 -> 9) and Device B sells 1 (Stock 10 -> 9) while offline:
    *   Server receives A: Stock becomes 9.
    *   Server receives B: Stock becomes 8.
*   **Correction**: If stock goes negative, backend allows it (soft constraint) or alerts user. Frontend shows negative stock until audit.

### 5.3 Sales
*   **Strategy**: Immutable Append-Only.
*   Sales cannot be modified. They can only be "voided" (which creates a negative transaction).
*   No conflict resolution needed.

## 6. Pseudocode Implementation

### Push Handler
```typescript
async function handlePush(req, res) {
  const { operations, deviceId } = req.body;
  const userId = req.user.id;

  await prisma.$transaction(async (tx) => {
    for (const op of operations) {
      // 1. Idempotency Check
      const existing = await tx.operation.findUnique({
        where: { clientOpId: op.clientOpId }
      });
      if (existing) continue;

      // 2. Process based on Type
      switch (op.opType) {
        case 'CREATE_PRODUCT':
          await tx.product.create({
            data: { ...op.payload, userId }
          });
          break;

        case 'UPDATE_PRODUCT':
          await tx.product.update({
            where: { id: op.entityId },
            data: { ...op.payload, version: { increment: 1 } }
          });
          break;

        case 'ADJUST_STOCK':
          await tx.inventory.update({
            where: { productId: op.entityId },
            data: {
              quantity: { increment: op.payload.delta },
              version: { increment: 1 }
            }
          });
          break;

        case 'CREATE_SALE':
          // Create Sale, Items, and decrement stock
          await processSale(tx, op.payload, userId);
          break;
      }

      // 3. Log Operation
      await tx.operation.create({
        data: {
          clientOpId: op.clientOpId,
          userId,
          deviceId,
          entityType: op.entityType,
          entityId: op.entityId,
          opType: op.opType,
          payload: op.payload,
          clientTimestamp: op.timestamp
        }
      });
    }
  });

  res.json({ success: true });
}
```
